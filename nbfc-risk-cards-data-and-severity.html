Risk Cards — Data Sources & Severity Logic

For every card on the Risk Alerts page: exactly which tables it reads, what it measures, and the thresholds that decide High vs Warning vs OK vs Inconclusive. Each card computes an affected fraction (affected units ÷ assessable population), then colours itself off that fraction against two cutoffs — the cutoffs differ per card and are listed in each ladder below.

How every card decides its severity

A card first counts affected units (vehicles/loans that trip its trigger) out of its assessable population (units it could actually measure — the rest are excluded, never counted as healthy). The ratio drives the colour via pickSeverity(fraction, high, warn):

High Alert
fraction ≥ the card's high cutoff
Warning
fraction ≥ the card's warn cutoff (but below high)
OK
tested, fraction below warn — genuinely clean
Inconclusive
assessable population = 0 (no data to test), or the query errored
Two structural rules that override the ladder. (1) Small books: the cutoffs are fractions tuned for large fleets (as low as 0.5%). On a 7-loan tenant, one affected vehicle = ~14% — which clears every card's High cutoff. So on small fleets, a single flagged vehicle usually = High, regardless of the numbers below. (2) Agent (LLM) cards are capped from High → Warning until a human promotes the hypothesis (E-188). Only the five human-written cards here, once seeded, can raise a true High.

Governed thresholds — the admin “Risk Rules” screen (nbfc_risk_rules)

These set what counts as “affected”. Read live per run and snapshotted into each card’s evidence_json.thresholds. If the DB is unreachable, the BRD default is used.

Card severity is computed live on page load from these evaluators, or read from the latest risk_card_runs row per (tenant, hypothesis) when a run has executed. All five human cards must be seeded in risk_hypotheses (source='human') or the page renders an empty, falsely-healthy 0/0/0/0.

⚠ Read this before you trust any red card on your screen The High Alerts tagged “AI” — Ignition Status Risk (7 / 7), High Demand Vehicles (5 / 7), Low Demand Vehicles (5 / 7), High Utilization Low DPD (4 / 5), High Utilization Borrowers (3 / 7) — were written by the language model, and several are among the 16 unverified (E-185) cards. The one red card without an “AI” tag — “7-day usage cliff, 1 of 5 assessed” — is real, computed arithmetic.

02 The one rule that decides if a card is trustworthy

Every risk card has a hidden verdict_source field. It is the single most important thing to check.

Tag / verdict_sourceWho produced the numberTrust
hand_codedA hand-written TypeScript evaluator did the arithmetic on real data. These are the 5 non-AI cards (7-day usage cliff, etc.).TRUST

noneNo verdict was computed (sandbox down / no code emitted).DON'T

Check it in the database directly:

SELECT h.slug, r.severity, r.verdict_source, r.affected_count, r.total_count
FROM risk_card_runs r JOIN risk_hypotheses h ON h.id = r.hypothesis_id
WHERE r.tenant_id = '<your-tenant-uuid>'
ORDER BY r.run_at DESC;
-- any verdict_source = 'legacy_llm' or 'none' → the number is NOT verified

04 CDS — Credit Default Score (0–100, higher = riskier)

Shown on Lead Intelligence and Battery Monitoring. It answers: “how badly is this borrower paying, weighted toward recent EMIs?”

The formula (BRD §6.1.5)

CDS = ( Σ(EMI_weight × recency) + streak_penalty + telemetry_risk ) ÷ ( Σrecency + 3.0 + 0.5 ) × 100

Inputs — the last 6 elapsed EMIs (due on/before today), newest first, from emi_schedules:

  • EMI_weight (how bad each EMI is): paid = 0 · paid-late ≤7d = 0.5 · paid-late >7d = 0.7 · overdue ≤7d = 0.6 · overdue 8–30d = 0.85 · overdue >30d / missed = 1.0 · not-yet-due = 0
  • recency: newest EMI ×1.0, then 0.88, 0.76, 0.64, 0.52, down to 0.40 (older EMIs count less)
  • streak_penalty: +0.5 for each consecutive most-recent missed/overdue EMI (resets to 0 the moment a recent EMI was paid)
  • telemetry_risk: 0 if battery reported ≤12h ago; ramps to 0.5 as it goes stale toward ~7 days. Read from the live IoT battery — 0 when the tunnel is down.

Even with a missed EMI, the score is a modest 24 — because the most recent EMI was paid (streak = 0) and recency down-weights the older miss. That is by design (recency-weighted), but it explains why CDS can look low despite past misses.

Correct math, two things to know 1. The telemetry piece is always 0 without the IoT tunnel — yet +0.5 stays in the denominator, so every CDS is slightly deflated and Confidence can never reach HIGH (it pins at MEDIUM). 2. The nightly snapshot job (borrower_risk_scores) reads a dead telemetry table (telemetry_ingestion_log, empty here) and skips loans whose id isn’t a UUID (e.g. BAJAJ-LIVE-…) — so the snapshot table is sparse. The displayed score dodges both by recomputing live from emi_schedules, so what you see on screen is correct.

05 PCI — Payment Consistency Index (0.0–1.0, higher = better payer)

The mirror of CDS — how consistently the borrower pays. Below 0.40 it fires a pci_low risk alert.

The formula (BRD §6.1.5)

PCI = Σ(EMI_score × weight) ÷ Σweight  (weight = n for newest … 1 for oldest; Σweight = n(n+1)/2)

EMI_score: paid on time = 1.0 · paid late (<7d) = 0.5 · missed/overdue = 0.0. Same 6-elapsed-EMI window from emi_schedules.

Correct — and one important bug already fixed The due_date ≤ today filter is load-bearing: without it, future “scheduled” EMIs (score 0) sort first and every borrower would show PCI 0.000. That filter is present in the live path and the nightly job, so PCI is sound. Division is guarded (empty history shows “—”, never a fake 0).

06 EMI Tracker — the five headline numbers

Money is stored two ways: EMI amounts in rupees (emi_schedules.amount), collections in paise (emi_payment_attempts.amount_paise, ÷100). The conversions are all correct — the one real error is “Collection rate”.

07 Battery Monitoring — telemetry tiles & columns

All live battery data (SoC, SoH, GPS, freshness, alerts) is read from a separate IoT server over an SSH tunnel, not the app database. When that tunnel is down, these go blank / “never” / 0 — so read them knowing the tunnel state.

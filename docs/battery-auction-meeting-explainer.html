Battery Recovery & Auction — how it works, what's live, what's left

When a financed battery loan defaults, the NBFC recovers the battery, iTarang inspects and optionally refurbishes it, and it is auctioned to dealers on the platform — paid in cash or financed again as a new loan. This document walks the whole flow in one pass.

7stages, recovery → resale
3portals: NBFC · Admin · Dealer
45API routes live
~90%of the BRD is built & working
1

The one-line pitch

A defaulted battery is dead money. This module turns it back into a performing asset — recovered, health-checked, optionally repaired, then sold to the highest-bidding dealer in a timed online auction. If the winning dealer takes finance instead of paying cash, the same battery starts a new loan and goes back on the road.

Only dealers can bid — never other NBFCs. The NBFC that owns the battery runs the auction; iTarang admin supervises; the platform automates the clock, the bidding rules and the notifications.

The whole flow in one picture

Two rules worth saying out loud: refurbishment is recommended, never mandatory (the bypass arrow is deliberate), and a battery below 55% state-of-health is scrapped, never auctioned.

3

The status journey

Every battery, lot and sale moves through a fixed set of statuses. The platform enforces each transition — you cannot skip a step or move backwards.

4

Who sees what — the three portals

NBFC · seller

Runs the recovery & the auction

  • Flags a defaulted loan → recovery board (kanban)
  • Registers the battery: serial, photos, location
  • 3-step inspection → health score → suggested price
  • Raises a refurbishment job (checklist, cost, new accessories)
  • Composes the lot: batteries, price, 2/12/24/48 h window, audience
  • Approves the winner, tracks the sale to delivery
iTarang · admin

Supervises every live auction

  • Auction Control Centre: pause / resume / extend time
  • Sets a reserve floor (before the first bid)
  • Can approve the winning bid on the NBFC's behalf
  • Ending an auction early needs a reason + MFA
  • Cancelling needs a second admin's approval
  • Analytics: sell-through, realisation, no-bid rate, engine health
Dealer · only bidder

Bids, wins, pays, redeploys

  • Live-auction carousel on the dashboard home
  • Browse with filters: condition, price, state, city, distance
  • Sees photos, health score, highest bid — never rival names
  • Bids live; can set a standing maximum (auto-bid)
  • Sees an EMI estimate before bidding on refinance lots
  • Pays by Razorpay; tracks purchases to delivery

There is also a public showcase page at /auctions — read-only, no prices below base, no bidder data. Bidding always requires a dealer login.

5

How dealers hear about a lot

When the NBFC publishes, they pick one visibility rule. The platform resolves it into a frozen list of eligible dealers and notifies each of them — once.

6

What's done ✅ vs what's left ⏳

We audited every screen, API route, database migration and background job against the BRD on 20 Aug 2026. The flow that is built is correct — it follows the approved design, and it fixed 8 of the 10 known engine defects along the way. Here is the honest scoreboard.

✅ Built and working

  • DONEFull recovery pipeline — flag → collect → intake with photos → inspection with health grading → optional refurbishment with checklist & cost tracking
  • DONELot building — drafts, multi-battery lots, derived pricing, reserve price, 2/12/24/48 h windows (48 h hard max)
  • DONEAudience targeting — India / states / cities / radius, with a live reach preview before publishing
  • DONEThe engine — opens & closes auctions automatically every 15 s, anti-snipe extensions, proxy auto-bidding, ties broken by earliest bid
  • DONEDealers-only bidding — the old NBFC bid route is shut; bidder names are never shown
  • DONEDealer experience — browse + 9 filters, live countdown, bid history, my-bids, purchases, Razorpay payment, dashboard carousel
  • DONEAdmin supervision — control centre, two-admin cancellation, analytics + engine health
  • DONENotifications — WhatsApp, email, in-app on publish / outbid / ending-soon / won / lost
  • DONEPublic showcase page (read-only)

⏳ Left to do

  • P0Production database update. Two migrations (E-252/E-253) are live on sandbox but not on production. Until they run, deploying this code crashes the NBFC recovery page and the dealer purchases screen. One script, five minutes.
  • P1Recording offline payments. Dealers are told they can pay by bank transfer, but the seller has no screen to record it — an offline sale is currently a dead end.
  • P1The refinance button. Everything exists — the lot type, the EMI preview, the loan-creation service — but no screen actually triggers it. Refinance wins currently settle as plain cash.
  • P2Failed-sale record. If a winner never pays, the sale is deleted instead of being marked failed — no audit trail.
  • P2Refinance → disbursement handoff. The new loan stops at "sanctioned"; nothing pushes it into disbursement.
  • P2Real MFA. The code admins type before destructive actions is not actually verified yet — any 6–8 digits pass.
  • P3Polish: link the public page from somewhere, register the SMS (DLT) template, add automated tests for the bidding engine, small code clean-ups.
The one thing that cannot wait: run the E-252/E-253 migrations on production before this branch deploys. Everything else can be scheduled; this one is a crash on day one.
7

Three decisions we need from this meeting

1 · Who owns the refinance loan?
The code currently assumes the selling NBFC finances the battery again. The alternative is to route it competitively, like a fresh origination, so any NBFC can win it. This changes who books the new asset — the code is flagged and waiting on this answer.
2 · Should admin approve a lot before it goes live?
Today an NBFC publishes straight to live — admin supervises but does not pre-approve. If a pre-publish approval gate is wanted, it is a deliberate addition, not a bug fix. Confirm the current behaviour is intended.
3 · When do we want paid promotion (BRD §19)?
The "promote this lot to a wider audience for a fee" revenue feature was deliberately deferred. The base now works, so it is cheap to add — it just needs a slot on the roadmap.

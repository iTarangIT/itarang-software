Before the chart

Two databases that have never met

Everything below exists to marry two halves that live on different machines, in different clouds, with no foreign key between them.

                        A RISK CARD
There is no foreign key, no shared transaction, no single database. The vehicle registration number is the only thing holding the two halves together. Every risk card is a sentence that combines one fact from each side.
Where the join key lives. On the loan side it is nbfc_loans.vehicleno. The wider mapping of device → battery → vehicle → dealer is device_battery_map (on AWS RDS) — that's the bridge table other telemetry screens use to resolve which vehicles belong to whom before querying the VPS. If a loan's vehicleno doesn't match a vehicle_state.vehicleno exactly, that borrower is simply invisible to every telemetry card — no error, just silently excluded.
There is a second, dormant ingestion path — don't confuse it with this one. POST /api/iot/ingest is a push endpoint (device → CRM, JWT-authed, ±5 min stale guard) that writes telemetry_events and telemetry_ingestion_log on AWS RDS. Nothing actually POSTs to it, so those tables are empty. The risk engine does not read any of them. All real telemetry arrives via the Intellicar → poller → VPS path charted below.

The master chart

End to end, top to bottom

Bands A–D run continuously, in the background — they are already finished long before anyone opens the page. Bands 1–9 are what a single click actually triggers.

Band ASource
Third party · not ours · pull only Intellicar API The company that makes the IoT trackers bolted to the e-rickshaws. They don't give us the raw radio signal — they give us a web API. This is the source of every fact about a vehicle. apiplatform.intellicar.in/api/standard · POST /gettoken → Bearer (cached 55 min) listvehicledevicemapping · getgpshistory · getbatterymetricshistory · getlatestcan · getdistancetravelled · getlastgpsstatus
If Intellicar is down, nothing downstream can invent the missing data. Every number you will ever see on a risk card entered the building through this one door.
Careful — there is a decoy in the repo. src/lib/intellicar/client.ts is a complete TypeScript Intellicar client with zero callers. It is dead code: a re-implementation of what the VPS poller already does. INTELLICAR_USERNAME / INTELLICAR_PASSWORD sit in .env.local and are never read at runtime. If you go looking for "where does the CRM call Intellicar", the honest answer is it doesn't — the poller does, and the poller is not in this repository.
Band BIngest
every 30s
Python · loop, every 30 s · on the VPS poller Wakes up, asks Intellicar "what's new?", writes down the answer. The API will not push to us, so we ask — forever. Intellicar API telemetry_gps · telemetry_can · telemetry_battery · vehicle_state · alerts
⇄
Redis · in-memory poller cache Scratch paper. Remembers "which packet did I last see for this vehicle" so it doesn't re-insert identical data every 30 s. nothing durable — wipe it and the poller just does one cycle of redundant work
If the poller stops, you get no error. Everything downstream keeps working and quietly serves older and older data. A stopped poller looks exactly like a fleet of parked vehicles — which is why the dpd-7-no-telemetry card cannot tell "the borrower unplugged the tracker" from "our poller died".
The poller lives on the VPS, not in this repo. You will not find it by searching the codebase. It also has a known defect worth knowing about: it re-inserts the latest CAN frame on every poll whether or not the device produced a new one, so ~96% of telemetry_can rows repeat a timestamp. That is why SOH degradation maths is noisy — roughly 100 genuinely distinct samples per battery per day.
Band CRoll up
automatic
TimescaleDB · continuous aggregate · self-refreshing distance_rollup A pre-computed daily kilometre total per vehicle. Nobody schedules this and no cron owns it — Timescale keeps it current by itself as new GPS rows land. raw telemetry (Timescale hypertable chunks) distance_rollup(time, vehicleno, distance_km, bucket_size='day')
Two of the five hand-coded cards — usage-drop-7d and low-utilization-active-loan — live or die on this one table.
Band DJoin
nightly
Python cron · NEVER RAN aggregator Was supposed to read the loan book from AWS RDS, read telemetry from the VPS, stitch them on vehicleno, and write dashboard_* tables back into the VPS. It has never run: aggregator_runs is empty. (would read) AWS RDS nbfc_loans + VPS raw tables (would write) dashboard_nbfc_loans_with_iot · battery_health_metrics · geofence_events · charge_events · fault_codes · immobilizer_state
This dead box is why iot-queries.ts is 985 lines. Because the aggregator's tables are empty, the CRM had to learn to do the aggregator's job live, on every request — roughly half that file is fallback code compensating for one process nobody ever started. It also caused a real shipped bug: low-utilization-active-loan originally read an aggregator table, found it empty, concluded every vehicle drove 0 km, and fired a false High Alert. The fix was to repoint it at distance_rollup, which maintains itself.

The risk engine does not use the aggregator, and does not use Redis. Neither appears anywhere in bands 1–9 below.

Failure path RunInFlightError → HTTP 409 "Analysis already running — wait for it to finish." A run still 'running' after 15 min is presumed dead and reaped, so a crash can't wedge the tenant forever.
Why: before this, double-clicking the button fired two complete workflows at the same tenant. Both wrote a full set of cards, and whichever finished last silently shadowed the other. The lock is a database constraint, not an application check — so it also holds between the nightly cron and a manual click.

Band 5LangGraph
node 2
LangGraph node loadCatalogue() Loads the AI-authored hypotheses we already have — and the Python they were tested by. A hypothesis with no stored code cannot be re-run, so it is skipped rather than guessed at. risk_hypotheses WHERE source='llm-v1' AND retired_at IS NULL AND test_definition->>'python_code' IS NOT NULL graph state: hypotheses[]
This is what makes a run reproducible. The catalogue used to be write-only: propose, test once, throw the code away, invent different ones next time. Nothing was ever re-measured, so no card could be compared to itself over time.

OpenAI · gpt-4o-mini · temp 0.2 planDimensions() Picks 3–4 risk themes to explore this run. PLAN_PROMPT + tenant display_name, active_loans ["asset_health", "behavioural_usage", "financial_repayment", …]

OpenAI · one call per dimension proposeHypotheses() Writes 1–2 new hypotheses per dimension — and the Python that tests each one. A proposal with no code is discarded on the spot. New slugs are de-duped against the entire catalogue. PROPOSE_PROMPT + dimension + every slug already taken [{slug, title, description, test_plan, python_code}]
THIS IS THE ONLY THING OPENAI DOES. It proposes the question and writes the code. It is never asked for a severity, never asked for a count, and its answer never reaches a card directly. Every number is computed downstream. 
# the contract every generated test must satisfy
def evaluate(loans, vehicle_states, daily_km):
    # loans          → DataFrame: loan_application_id, vehicleno, current_dpd, emi_amount, outstanding_amount
    # vehicle_states → DataFrame: vehicleno, online, last_gps_at, sec_since_gps, lat, lon,
    #                             speed_kph, ignition, soc_pct, soh_pct, pack_voltage, pack_temp_c
    # daily_km       → DataFrame: day, vehicleno, km   (last 14 days)
    return {"severity": "high"|"warn"|"ok", "affected_count": int, "total_count": int,
            "finding_summary": str, "evidence": {"sample_rows": [...], "notes": [...]}}

# pandas + numpy only. no imports, no file I/O, no network, no exec/eval. under 60 lines.
Band 7LangGraph
node 5
sandbox
LangGraph node · the only place severity is decided runTest() Health-checks the sandbox once, fetches the tenant's data once, then executes each hypothesis's stored Python against it.
Builds the payload fetchSandboxData() One fetch, reused for every hypothesis in the run. Three arrays that become three pandas DataFrames. RDS nbfc_loans · VPS getVehicleStates() · VPS getDailyKm(vnos, 14) {loans[], vehicle_states[], daily_km[]}
→
FastAPI · Docker · 127.0.0.1:8091 → :8000 · loopback only POST /execute A soundproof room for code an AI wrote 30 seconds ago. An AST allowlist (not a blocklist) rejects anything that isn't pd, np, the three DataFrames, and ~20 safe builtins — no imports, no eval/exec/open, no __-prefixed attribute (that's the __subclasses__ escape), and no module-level statement other than def evaluate. {hypothesis_slug, code, data:{loans, vehicle_states, daily_km}} + Bearer SANDBOX_TOKEN {ok, result:{severity, affected_count, total_count, finding_summary, evidence}, elapsed_ms}
The sandbox has no database connection of its own. The CRM ships the DataFrames with the request. That is what makes it safe to hand it model-authored code: even a malicious evaluate() has nothing to reach for. It answers with a verdict and forgets everything — stateless by design.

There is deliberately no LLM fallback here. Ask a model to state an affected_count and it will produce a number that looks exactly like a measured one and isn't. Before E-185, that is precisely what happened when the sandbox was down: the engine asked gpt-4o-mini to state the severity, and 84 out of 84 rows came back ok — a perfectly healthy portfolio, invented. Those numbers landed in the same columns and rendered in the same chip as the computed ones. That fallback is gone. When we cannot execute, the card says so.

The first-load fallback: if a hand-coded hypothesis has no stored run at all, the page runs its evaluator live, on the spot, so a brand-new tenant isn't staring at an empty screen — that's the "Never run — computed live on page load" notice. An AI hypothesis with no stored run has no evaluator to fall back on, so it honestly renders as "Never tested."

The denominator is the whole game. Each card scores against the population it can actually measure, not the whole loan book. A vehicle with no GPS history has no home base, so it is excluded from geo-shift rather than counted as "not diverted". That's what 4 / 5 affected on a card means: four of the five loans we could assess.
Scope, stated plainly. The risk engine's only input from the CRM database is nbfc_loans. It does not read borrower_risk_scores or emi_schedules. Everything else it knows comes from the VPS.

What breaks what. Tunnel down → every hand-coded card throws → amber banner, cards render as error. Sandbox unset → every AI card is inconclusive. Poller stopped → cards stay green and silently describe a week-old fleet. OPENAI_API_KEY missing → "Re-run analysis" throws immediately. None of these can ever turn a card green. That is the entire design.

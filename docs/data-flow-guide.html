How Data Travels from the UI to the Database

The full round trip, told through one real feature in this repo: the “Create Lead” form in the Inside Sales dashboard. Every file path and code snippet below is real — open them and follow along.

🖥️ Form→ 📡 fetch()→ 🚪 Middleware→ ⚙️ API Route→ ✅ Zod→ 🗺️ Drizzle→ 🐘 PostgreSQL

…then the response travels all the way back up, and the screen refreshes. That’s the whole loop.

The journey, step by step

Blue steps = the request going down. Green steps = the response coming back up.

1
Request ↓

The form — where data is born

A sales rep types a dealer’s name and phone into a modal. React keeps each field in useState — the data only exists in the browser’s memory at this point.

src/app/(dashboard)/inside-sales/_components/modals/CreateLeadModal.tsx 
const [dealerName, setDealerName] = useState("");
const [phone, setPhone] = useState("");
// ...user types; React re-renders the inputs on every keystroke

Simple version: the data starts as plain JavaScript variables in the browser. Nothing is saved yet — refresh the page and it’s gone.

2
Request ↓

Submit — the data leaves the browser

On submit, the component packs the fields into JSON and mails it to the server with fetch(). This is the moment data leaves the UI.

CreateLeadModal.tsx — lines 87–98 
const res = await fetch("/api/inside-sales/lead/create", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
        dealer_name: dealerName.trim(),
        phone: phoneDigits,          // "9876543210"
        city: city || null,
        interest_level: interest || null,
    }),
});

Simple version: think of it as putting the form data in an envelope (JSON) and addressing it to a URL. The URL is the address of a server file (see step 4).

3
Request ↓

Middleware — the doorman in the lobby

Every request passes through middleware.ts first. For pages it redirects users based on their role; for /api/* requests it just refreshes the Supabase login cookie and waves them through — real security happens inside the route.

src/middleware.ts 
// API routes handle their own auth — middleware only refreshes the session
const isPublicRoute = path.startsWith("/api") || ...;
await supabase.auth.getUser(); // keeps the login cookie fresh

Simple version: a doorman who checks your badge is still valid, but doesn’t decide what rooms you can enter. That check comes next.

5
Request ↓

Zod validation — the quality inspector

Never trust what the browser sends. A Zod schema describes exactly what valid data looks like; parse() throws if anything is off, and the wrapper turns that into a clean 400 error.

route.ts — lines 18–33 
const BodySchema = z.object({
    dealer_name: z.string().trim().min(2).max(200),
    phone: z.string().trim().regex(/^\d{10}$/, "Phone must be exactly 10 digits"),
    interest_level: z.enum(["hot", "warm", "cold"]).optional().nullable(),
});
const body = BodySchema.parse(await req.json()); // throws → 400 if invalid

Simple version: a checklist at the door — “name at least 2 letters, phone exactly 10 digits.” Fail the checklist and the data never reaches the database.

6
Request ↓

Drizzle — the translator that speaks SQL

The route calls db.insert(...). Drizzle (the ORM) turns this TypeScript into a real SQL INSERT INTO dealer_leads ... and sends it over the connection defined in src/lib/db/index.ts.

route.ts — lines 55–78 
await db.insert(dealerLeads).values({
    id,                              // "DL-1719900000000-aB3xK9pQ"
    dealer_name: body.dealer_name,
    phone: body.phone,
    lead_status: "New_Unassigned",
    source: "manual_upload_lead",
    created_at: now,
});

Simple version: you write TypeScript, Drizzle writes the SQL. The shape of what you can insert comes from the table definition in the schema file (next step).

7
Request ↓

PostgreSQL — the data finally lands

The row is written to the dealer_leads table in PostgreSQL (AWS RDS). The table’s shape lives in one giant file every developer here should bookmark: schema.ts.

src/lib/db/schema.ts — line 2954 
export const dealerLeads = pgTable("dealer_leads", {
    id: text().primaryKey().notNull(),
    dealer_name: text("dealer_name"),
    phone: text().unique("dealer_leads_phone_unique"), // ← no duplicate phones
    lead_status: varchar("lead_status", { length: 50 }),
    created_at: timestamp("created_at").defaultNow(),
    ...
});

Simple version: the data is now permanent — it survives refreshes, restarts, everything. The UNIQUE rule on phone is enforced by the database itself, the last line of defense.

🔄 The turn-around — now the answer travels back up
8
Response ↑

The route replies with JSON

The insert succeeded, so the route sends back a small JSON receipt using the shared helper successResponse (from src/lib/api-utils.ts).

route.ts — line 87 
return successResponse({ id });
// browser receives: { "success": true, "data": { "id": "DL-…" }, "timestamp": … }

Simple version: the server mails an envelope back: “Done. Here’s the new lead’s ID.”

9
Response ↑

The UI reacts — toast + refresh

Back in the modal, the await fetch() from step 2 resolves. On success: a toast pops, the form resets, and the parent invalidates React Query caches — which automatically re-fetches the lead list so the new lead appears on screen.

CreateLeadModal.tsx (lines 99–103) → QueueView.tsx (lines 169–175) 
// CreateLeadModal.tsx
toast.success("Lead created — find it in the Unassigned (Claim) tab.");
onSuccess();

// QueueView.tsx — the parent decides what "refresh" means
queryClient.invalidateQueries({ queryKey: ["inside-sales-queue"] });
queryClient.invalidateQueries({ queryKey: ["inside-sales-counts"] });

Simple version: “invalidate” = “this cached list is stale, go fetch it again.” That re-fetch is a brand-new trip through steps 2–8 (a GET this time), and the new lead shows up. Full circle. ✅

💡

One thing that surprises everyone: there are TWO databases

Supabase only handles identity — logins, sessions, cookies. All business data (leads, dealers, calls…) lives in AWS RDS PostgreSQL, reached through Drizzle via src/lib/db/index.ts. So requireRole asks Supabase “who is this?”, then asks the RDS users table “what’s their role?”.

“Where do I look?” — the navigation cheat sheet

The same pattern repeats for every feature. Learn these five locations and you can trace any flow in the repo.

src/app/(dashboard)/…

The screens. Pages & components users see, grouped by role (inside-sales, admin, dealer-portal…). Forms and buttons start here.

src/app/api/…/route.ts

The endpoints. The URL path mirrors the folder path exactly. See a fetch("/api/x/y") in a component? The handler is at src/app/api/x/y/route.ts.

src/lib/db/schema.ts

The tables. Every one of the 40+ database tables, defined in TypeScript. Ctrl+F a table name to see its columns.

src/lib/auth-utils.ts

The bouncer. requireAuth / requireRole — called at the top of almost every API route to check login + role.

src/middleware.ts

The doorman. Runs before every request: refreshes the session cookie and redirects page visits based on role. Doesn’t gate /api/*.

src/lib/api-utils.ts

The envelope factory. successResponse, errorResponse, withErrorHandler — every API reply is shaped here, so all responses look the same.

When things go wrong — errors travel the same road back

A rejected request just turns around earlier. The status code tells you which checkpoint said no.

400

Zod said no

Data failed validation (step 5) — e.g. a 9-digit phone. withErrorHandler catches the ZodError and replies with field-level details. Never reached the DB.

401 / 403

Auth said no

requireRole (step 4) found no valid login (401) or a role that isn’t allowed to create leads (403). Rejected before validation even ran.

409

The database said no

A lead with that phone already exists. The route pre-checks it, and the UNIQUE constraint on dealer_leads.phone backs it up at the DB level.

In every case the modal’s catch block (step 9’s twin) shows the message in a red toast — errors ride the exact same response path as successes.

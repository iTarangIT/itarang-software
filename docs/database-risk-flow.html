3 · “Re-run analysis” — button to storage

One click, traced through every function and every table it touches, in call order.

The whole chain is synchronous — no queue, no job runner. The button holds an open HTTP request for 30–120 s while an LLM writes Python, a sandbox runs it, and the cards land in Postgres. Line references are to the source as of 17 Jul 2026.

app — Next.js / Node rds — CRM Postgres (database-2) iot — VPS telemetry Postgres ext — outside the box
Two databases, never joined by the engine. The loan book lives in CRM Postgres; telemetry lives on a separate VPS Postgres reached through getIotSql(). Nothing in this flow writes borrower_risk_scores, risk_alerts or nbfc_score_runs — those belong to the separate CDS/PCI path. This flow writes exactly three tables: risk_runs, risk_hypotheses, risk_card_runs.

The other caller — same workflow, same lock

The button is not the only way in, and it is not the one that keeps the data fresh.

⏱
VPS crontab · 30 1 * * * · maxDuration 800 s · not Vercel cron GET /api/cron/nbfc/risk-analysis (Bearer $CRON_SECRET) Sweeps every active tenant through the identical workflow, sequentially — parallel would stampede OpenAI and the single sandbox. A tenant whose run is already in flight is reported skipped, never queued. READ nbfc_tenants ← listActiveTenants() runRiskWorkflow(tenant, { trigger:'cron' }) → same partial unique index
Both non-production auth bypasses are real. The cron's isAuthorised() returns true for any request when NODE_ENV !== "production", and requireNbfcAccess() has a dev bypass when there is no session and NBFC_DEMO_TENANT_SLUG is set. Fine locally; worth knowing before either is exposed.

Everything this flow writes

Three tables. Nothing else in the database is touched by a click.

TableWritten byWhat lands there
risk_runs beginRiskRun · reapStaleRuns · completeRiskRun / failRiskRun One row per run. Holds the lock while status='running'; ends with counts and token spend.
risk_hypotheses writeCards · retireIfPersistentlyBroken · promote route The question being asked, and for AI ones the Python that answers it. Soft-retired, never deleted.
risk_card_runs runHandCodedCards · writeCards One row per hypothesis per run — the card you see. Append-only; the page takes the newest per hypothesis.
Empty tables detected with count(*); empty columns with count(<col>), which ignores NULLs — a result of 0 against a non-zero row count means the column is NULL throughout. Counts are exact, not planner estimates.

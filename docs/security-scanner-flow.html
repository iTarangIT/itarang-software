How the scanner finds a bug and turns it into a card

A LangGraph agent drives a real browser through your CRM, deterministic probes attack each endpoint, findings are written to Postgres, and the dashboard reads them back. This traces the whole path — every file, function, and table — and shows exactly where each card's data comes from.

02

Stage by stage — the real files

Everything lives under src/lib/security/ (the agent) and src/app/(dashboard)/admin/security/ (the UI).

1 Trigger

A CLI run or the “Run Scan” button. The button POSTs, takes the lock, then kicks the scan in the background with Next’s after() so the request returns instantly.

filescripts/security-scan.ts · api/admin/security/scan/run/route.ts
callsrunSecurityScan({ trigger })

2 Engine setup

Resolves the target (refuses prod unless SECURITY_ALLOW_PROD=1), inserts a running row that is the single-flight lock, then logs each role in through the real /login page and saves its cookies.

fileengine.ts · target.ts · scan-run.ts · session.ts
outrunId + per-role browser sessions

3 LangGraph agent

A compiled StateGraph. plan_targets asks GPT for extra API paths to test; run_probes runs every probe; llm_triage dedups & writes plain-English remediation; write_findings persists.

fileagent/graph.ts · agent/tools.ts
modelChatOpenAI (gpt-4o-mini) — optional

4 Probes attack

Each probe fires real HTTP at your CRM — as nobody, and as a logged-in dealer — and returns RawFinding[]. The probe sets the severity from a fixed rule (e.g. PII in an unauth response → critical).

fileprobes/{exposure,authz,idor,injection,upload_headers}.ts
outRawFinding{ severity, title, target_url, evidence… }

5 Persist

Computes a fingerprint = sha256 of (check · method · path · title), then upserts into security_findings. The same bug found twice updates one row instead of piling up — that’s the de-dup you saw (8→7).

fileengine.ts → persistFindings()
outrows in security_findings + counts on the run

6 Dashboard reads

A Server Component queries the table (status open/acknowledged), groups by severity for the tiles, and hands the list to client cards. No API round-trip — direct Drizzle read on page load.

fileadmin/security/page.tsx → load()
outKPI tiles + finding cards + drawer
03

Trace one real card, end to end

Following your actual CRITICAL finding at /api/dealer-onboarding/list from attack to pixel.

The probe makes an unauthenticated request

unauthDataProbe (in probes/exposure.ts) walks a list of sensitive routes and GETs each one with no session cookie.

// probes/exposure.ts
const f = await get(ctx.anon, baseUrl, "/api/dealer-onboarding/list");  // anon = no cookies

The response comes back with data — and PII

The endpoint returns 200 with rows. looksLikeData() confirms it’s real data; detectPii() runs regexes for PAN / GST / IFSC / bank / phone.

if (!looksLikeData(f)) continue;
const pii = detectPii(f.body);            // ["PAN","GSTIN","IFSC"…]
const severity = pii.length ? "critical" : "medium";   // ← the rule

The probe emits a RawFinding — severity already decided

No LLM involved in this decision. Severity is critical because PII was present in an unauthenticated response.

{ check_slug:"unauth-data-exposure", category:"exposure",
  severity:"critical", confidence:"confirmed",
  title:"Unauthenticated PII exposure at /api/dealer-onboarding/list",
  target_url:"/api/dealer-onboarding/list", evidence:{ pii, status:200 } }

LangGraph collects it, the LLM polishes wording only

run_probes gathers all findings; llm_triage may improve the remediation sentence, set confidence, and drop duplicates — but it is forbidden from changing severity.

write_findings upserts it into Postgres

persistFindings() fingerprints it and writes one row. Re-scan and it updates the same row (partial-unique on fingerprint while status ≠ resolved).

// engine.ts
db.insert(securityFindings).values({ …finding, fingerprint })
  .onConflictDoUpdate({ target: fingerprint, targetWhere: "status <> 'resolved'" });

The dashboard reads it back and renders the card

load() selects it (status is open), FindingCard paints the title + red severity dot, and clicking opens FindingDrawer with the evidence, reproduction and remediation.

Where the data lives

Three tables, created by migration drizzle/E-215_security_scanner.sql — completely separate from the NBFC risk tables.

One row per scan. Its status='running' row is the lock so two scans can’t collide.

Catalogue of every probe (seeded automatically from probe metadata).

slugcategory owasp_refmutating

The source of every card. One row per de-duplicated vulnerability.

05

Where the LangChain logic lives

Two files: agent/graph.ts (the LangGraph StateGraph + ChatOpenAI) and agent/tools.ts (the tool() definitions).

NodeWhat it doesLLM?Can it set severity?
plan_targetsLooks at the dealer-onboarding page, asks GPT for extra /api paths worth probingyes—
run_probesRuns every deterministic probe against the CRMnoyes — the rules do
llm_triageDedups near-duplicates, writes remediation text, sets confidenceyesno — forbidden
write_findingsUpserts the enriched findings into Postgresno—
🔒

The golden rule. The language model plans and narrates, but every severity and every finding comes from deterministic probe code. If GPT is offline (no OPENAI_API_KEY), the scan still runs and still finds everything — you just lose the auto-written remediation prose. This is why the numbers you see are trustworthy, not hallucinated.

06

How each card gets its numbers

Three surfaces on /admin/security, all fed by one query in page.tsx → load().

The 5 KPI tiles

A count of active findings grouped by severity. SeverityStatCards receives a plain counts object.

counts[severity]++ over the query result

Each finding card

One card = one row in security_findings. The red/amber dot is severity; the text is title + summary.

FindingCard finding={row}

The detail drawer

Opens the full row — evidence_json, reproduction, remediation — plus triage buttons that PATCH the row’s status.

PATCH /api/admin/security/findings/[id]

📄

The exports too. Excel / PDF / Word all call loadReportData() — the same filtered query — so a downloaded report always matches exactly what’s on screen.

The whole system in one line: runSecurityScan → StateGraph (plan → probes → triage → write) → security_findings → /admin/security. Probes decide severity; the LLM only assists. Every card is a row; every row was proven by a real request to your own CRM.

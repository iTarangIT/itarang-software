Purpose, actors & permissions

Purpose. When a battery loan defaults, the financed battery is a stranded asset on the NBFC's book. This module recovers it, grades it, optionally refurbishes it, and resells it to a dealer through a timed online auction — for cash, or for cash plus a fresh loan (refinance) that puts the battery back on the road under a new borrower.

Scope. Everything from the moment a loan is flagged for recovery to the moment the sold battery is delivered (and, where chosen, refinanced). Out of scope: loan collection prior to recovery, disbursement of the refinance loan (parked, see §10), paid promotion (§19 of the source BRD, deferred).

S3Inspect & grade

A 3-step evaluation wizard captures state-of-health, physical condition, BMS status and a repair plan, then derives the base auction price automatically.

Actor
Collection centre / NBFC
Screen
BatteryEvaluationPanel.tsx → BatteryEvaluationWizard.tsx
API
POST /api/nbfc/recovery/[id]/evaluation · stage moves via PATCH …/[id]/stage
DB writes
nbfc_battery_evaluations: step 1/2/3 JSON, photo_urls[], condition_grade, base_auction_price
  • Price bands (of market reference): SOH > 85 → 0.675× · SOH ≥ 70 → 0.575× · below → 0.40×
  • Grades: SOH ≥ 70 → refurbished-eligible · 55–70 → partial_working · < 55 → scrap (terminal, sold to scrap vendor)
  • The SOH gates are enforced server-side on the transition (stages.ts assertSohAllowsStage()) — a direct API call cannot sneak a 30%-SOH battery into refurbishment. A missing SOH reading fails safe to partial_working.

S4Refurbish — optional, never mandatory

The NBFC raises a job; the iTarang workshop repairs the battery and returns it. A battery that needs no repair takes the bypass arc from inspection straight to ready-for-auction.

Actor
Workshop (iTarang), raised by NBFC
Screen
Recovery → Refurbishment · RefurbishmentConsole.tsx
API
POST /api/nbfc/recovery/refurbishment · PATCH …/refurbishment/[id]
DB writes
refurbishment_jobs: checklist JSON, estimated vs actual cost, accessories, status, returned_at
  • Job lifecycle: requested → in_progress → returned (or cancelled, which drops the battery back to inspected, not ready).
  • Only one open job per battery (enforced in refurbishment.ts).
  • Accessories are always new — charger, harness, SOC meter (~₹7–8k) — costed per unit and rolled into the base price so the dealer sees one number.

S5Build & publish the lot

The four-panel Lot Composer: basics → items → pricing → window & visibility. Lots are draft-first — nothing goes live until the NBFC explicitly publishes (the old auto-publish-on-ready is gone).

Actor
NBFC
Screen
LotComposer.tsx (compose / drafts / new) · SellerLotsConsole.tsx
API
POST /api/nbfc/auction/lots (draft) · …/lots/[id]/items · PATCH …/lots/[id] · POST …/lots/[id]/publish · POST …/audience/preview
DB writes
auction_lots (+ seller_tenant_id, auction_type, starts_at, reserve_price, anti_snipe_seconds), auction_lot_items, auction_lot_visibility, auction_lot_audience (frozen)
  • Windows fixed to 2 / 12 / 24 / 48 h, validated server-side, 48 h hard maximum. Start now, or schedule.
  • A lot may mix conditions — new | refurbished | partial_working lives per item, not per lot (EVs later, same column).
  • Auction type: cash or cash_refinance. Bid increment auto-derived (2% of base, rounded to ₹100). Reserve price optional.
  • Audience is resolved and frozen before the status flips; a live reach preview runs while composing, and publish is blocked when it reaches 0 dealers.
  • Batteries in a published lot are reserved (ready → lotted); discarding a draft releases them.

S6Live bidding

Dealers see photos, health score, quantity, location and the highest bid — never a rival's name. The platform enforces every rule inside a row-locked transaction.

Actor
Dealer + Platform
Screen
AuctionBrowser.tsx → LotDetail.tsx (15 s detail poll + 2 s state poll)
API
POST /api/dealer/auctions/[id]/bid · …/auto-bid · GET …/state
DB writes
auction_bids (append-only, bidder_dealer_id), auction_auto_bids, audit log
  • Three gates in order: dealer role → membership of the lot's frozen audience → bid ≥ current + increment, with an explicit binding-bid confirmation.
  • Anti-snipe: a bid inside the final anti_snipe_seconds (default 120) extends the deadline by the same window — audited, and surfaced to bidders in the UI.
  • Proxy auto-bid: a dealer sets a standing maximum; the engine (running inside the bid transaction) advances the price eBay-style — the winner pays what it took to win, not their maximum. Exhausted orders are flagged; an outbid-by-proxy result is reported honestly, never as "bid placed".
  • The old NBFC bid route answers 403 (auction_nbfc_bidding_withdrawn) — dealers only, structurally.

S7Close & award

The scheduler — a 15-second in-process ticker — opens scheduled lots and closes elapsed ones. No human is needed for a lot to end on time.

Actor
Platform, then NBFC (or admin)
Screen
SellerLotDetail.tsx ("Award to highest bidder") · admin AuctionControlCentre.tsx
API
POST /api/nbfc/auction/lots/[id]/approve-winner · POST /api/admin/nbfc/auction/lot/approve-winning-bid · GET/POST /api/cron/auction/tick
DB writes
auction_lots.status = ended, auction_settlements (payment_pending, unique per lot), batteries → sold
  • Close claims the lot with FOR UPDATE SKIP LOCKED in one transaction; the top bid is ORDER BY amount DESC, placed_at ASC — ties go to the earliest bid.
  • A settlement is created only when a top bid exists and the reserve is met; otherwise the batteries return to ready for auction for re-listing.
  • The top bid is suggested; the seller (or admin, on their behalf) has the final say. Both paths converge on the same approveWinningBid().

S8Settle & pay

The winning dealer pays in full — online through Razorpay, or offline by bank transfer — then the seller dispatches and confirms delivery.

Actor
Dealer (pay) + NBFC (dispatch)
Screen
Dealer → Purchases (Purchases.tsx) · NBFC → AuctionSettlementsTable.tsx
API
POST/PATCH /api/dealer/auctions/settlements/[id]/pay (Razorpay) · POST/DELETE /api/nbfc/auction/settlements/[id]/payment (offline / abandon) · PATCH /api/nbfc/auction/settlements/[id] (status)
DB writes
auction_settlements: payment_ref, payment_provider, paid_at, status advance
  • Payment before dispatch: payment_pending → in_transit is refused until a payment is recorded (paid_at set).
  • Lifecycle: payment_pending → in_transit → delivered; delivery marks the batteries resold.
Gap (G2): the offline-payment route exists but has no screen — the dealer is told "the seller will record your bank transfer", and the seller has nowhere to do it. See §9, Phase B.

S9Refinance loop — the battery becomes a loan again

On a cash_refinance lot, the winner can take part cash / part loan: a sanction is raised against the winning dealer at the used-asset amount (≈₹40k vs ₹60k new), seeded from the auction — the dealer saw the same EMI split before bidding.

Actor
NBFC (raises the sanction)
Service
refinance.ts createRefinanceSanction() — idempotent; shared split math in lib/auction/refinance-split.ts
API
POST /api/nbfc/auction/settlements/[id]/refinance
DB writes
loan_sanctions row (status = sanctioned), auction_settlements.refinance_loan_id, audit log
Gap (G3 + G5): the route and service are complete, but nothing in any portal calls them — refinance wins currently settle as cash. And the raised sanction stops at sanctioned: the handoff into disbursement is not wired. See §9 and the ownership decision in §10.

Three chained state machines — the battery, the lot, the sale — each enforced at the service layer. The bypass arc and every branch below are deliberate.

Visibility & notifications

Who may see and bid on a lot is decided once, at publish, and frozen. Late-approved dealers do not join a running auction; re-publishing never re-notifies.

Visibility scopes — pick exactly one

ScopeParametersMeaning
india—every eligible dealer, no geographic filter
statestates[]one or many states (case-normalised match)
citycities[]one or many cities (normalised match)
radiuscentre lat/lng + kmhaversine distance from the lot's centre; dealers with an unknown city are excluded

Eligibility on top of geography: account active + onboarding approved + role dealer. NBFC users are excluded by role, never by geography — the exclusion holds even when an NBFC user sits inside the radius. Resolver: src/lib/nbfc/auction/audience.ts resolveAuctionAudience().

Notification events

Event keyFires whenAudience
auction.lot_publisheda lot goes liveevery dealer in the frozen audience
auction.outbida dealer's leading bid is beaten (incl. by proxy)the displaced bidder
auction.ending_soonthe final hour — idempotent, fires once per lotaudience + participants
auction.won / auction.lostclose + awardwinner / losing bidders
auction.paused / resumed / cancelledadmin lifecycle actionsaudience + participants

All fan-out is best-effort and try-caught — a bounced email can never fail a close. The dealer home also carries the live-auctions carousel (LiveAuctionsStrip.tsx, 5 s poll, max 8 lots).

Open business decisions

IDQuestionContextRecommendation
D1 Who owns the refinance loan? The code assumes the selling NBFC finances the battery again (flagged in refinance.ts). The alternative routes it competitively like a fresh origination. Start with the selling NBFC (already built, simplest settlement story); revisit competitive routing once volumes justify it.
D2 Should admin pre-approve a lot before it goes live? Today an NBFC publishes straight to live; admin supervises after the fact (pause / cancel / reserve). Keep publish-direct — the supervision toolkit already covers abuse; a pre-approval gate would add hours of latency to 2-hour auctions.
D3 When to build paid promotion (§19)? Deferred by design. It is a campaign row pointing at an existing lot plus a widened audience — no new pipeline. Schedule after Phase B, once real dealers are bidding — promotion is worthless before there is an audience to promote to.

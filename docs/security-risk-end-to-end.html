This page explains, in plain language, everything behind the Security Risk screen at /it/security: who starts a scan, what tool actually attacks the app, where LangChain and LangGraph sit, which functions run in which file, what kinds of threats can be found, which database tables are written, and how the fix-it chat writes real code back to disk.

Every box below shows the file path and the function() inside it, plus what data goes in and what goes out.

1 · The 10-second version

A human (IT role) clicks Run Scan, or a developer runs npm run security:scan
Nothing scans on a schedule today. Somebody has to start it.
↓
A real Chromium browser logs into the CRM as 4 different roles
Playwright — not a fake HTTP client. It types into the real /login form.
↓
An AI agent runs 4 steps: plan → probe → triage → write
The AI only suggests extra URLs and tidies wording. It never decides how dangerous something is.
↓
8 deterministic probes actually attack the app and decide severity
Plain TypeScript + regex rules. This is what produces every card you saw on the screen.
↓
Findings are written to Postgres
Re-scanning updates the same row instead of creating duplicates.
↓
/it/security reads those rows and paints the cards; you can chat with an AI to fix each one
The single most important rule in this whole system: severity (Critical / High / Medium / Low) is always set by a hard-coded probe rule in TypeScript — never by the language model. The comment enforcing this is at src/lib/security/agent/graph.ts:156 (“you MUST NOT change or invent severity”) and again at src/lib/security/severity.ts:9.

Node 2 — run_probes no AI at all

src/lib/security/agent/graph.ts:94 runProbes(state) → probesForMode(ctx.mode) → probe.run(ctx)
This is the node that actually finds the vulnerabilities on your screen. It:
  • picks the probe list for the mode (safe drops every mutating probe);
  • upserts each probe's metadata into the security_checks catalogue via seedCatalogue();
  • runs each probe in a try/catch — one broken probe never kills the scan;
  • then sweeps the LLM's extraTargets for unauthenticated data, tagging those findings evidence.discoveredBy = "agent" and titling them “(agent-discovered)” so you can tell them apart.
DB INSERT … ON CONFLICT (slug) DO UPDATE → security_checks
raw: RawFinding[] — with severity already decided
↓

Node 3 — llm_triage uses LangChain

src/lib/security/agent/graph.ts:143 llmTriage(state) → parseTriage(text)
Sends a compacted list (index, slug, title, url, 300-char summary — not the whole evidence blob) and asks for JSON edits. The model is allowed to touch exactly four things: remediation, owasp_ref, cwe_ref, confidence, plus a drop:true flag for duplicates. Severity is read from the probe, never from the response — see the comment on line 172. If the call fails, it returns the raw findings unchanged.
raw findings (compacted)
enriched findings (deduped, better wording, OWASP/CWE tags)
more token counts, added to the running total by the reducer
↓

Node 4 — write_findings

src/lib/security/agent/graph.ts:192 writeFindings(state) → deps.persist(state.enriched)
Calls back into the engine's persistFindings() (next section) and stores the returned counts in state.

Why LangGraph is worth it here

  • The order is guaranteed. Planning must finish before probing (probing consumes extraTargets); triage must finish before writing. The graph makes that a structural fact, not a comment someone can break.
  • State is typed and merged for you. promptTokens uses an adding reducer, so two different nodes each spending tokens produce one correct total with zero plumbing.
  • Each step fails alone. Every node catches its own errors and returns a safe partial state, so a dead OpenAI key degrades the scan instead of aborting it.
  • Room to grow. Adding a “re-verify a finding” node or a conditional “only triage if raw.length > 0” edge is a one-line change to the graph, not a rewrite of the engine.
  • Same house pattern. The NBFC risk engine uses the identical shape at src/lib/ai/langgraph/risk-hypothesis-graph.ts — two features, one mental model. They share no tables and no code.

The shared helpers every probe leans on

src/lib/security/probes/util.ts rawGet(rc, url, opts)
GET with maxRedirects:0, never throws on 4xx/5xx, and retries 3× with backoff on ECONNREFUSED / socket hang up — because a cold Next dev server drops the first hit while it compiles a route.
looksLikeData(f)
The “is this actually a leak?” test. Must be 2xx, and the body must not be empty / [] / {} / null. Stops empty lists being reported.
detectPii(body)
Six Indian-PII regexes: PAN, GSTIN, IFSC, Aadhaar, bank-account numbers, phone numbers. A hit here is what upgrades a finding to critical.
harvestId(ctx)
Grabs a real UUID from /api/dealer-onboarding/list, /api/dealer-onboarding/my or /api/leads/summary (dealer session first, anon as fallback) so IDOR has a genuine object to ask for. No id → the IDOR probe skips itself.

6 · Part E — Saving findings into the database

src/lib/security/engine.ts:111 persistFindings(runId, baseUrl, raw) · fingerprint(f, path)
Each finding gets a stable identity: sha256(check_slug | http_method | pathname | title).slice(0,64). Duplicates inside one run are dropped in memory; across runs, the insert uses ON CONFLICT (fingerprint) WHERE status <> 'resolved' DO UPDATE. So re-scanning refreshes the existing card instead of stacking a new one — and critically, it never overwrites your triage status. A resolved finding that comes back gets a new row.

Auto-apply — this writes live source code
src/app/api/it/security/findings/[id]/resolve/route.ts POST() · makeDiff()
Six hard rails, in order:
  1. Off by default — without SECURITY_AUTOFIX_ENABLED=1 it returns 409 + the diff for you to apply by hand.
  2. The model's file path is not trusted — the file is re-located server-side from target_url.
  3. Must be inside src/ and end in .ts/.tsx.
  4. The search string must occur exactly once. Zero → 409 “code no longer matches”. Two+ → 409 “ambiguous”. It never guesses.
  5. Writes a .bak backup, then the change, then re-reads and verifies it.
  6. Any failure → the original content is written straight back. The app can't be left broken.
the .ts file on disk + a .bak sibling

The audit trail behind the History tab
src/lib/security/resolution-audit.ts recordFindingAction(input) · requestOrigin(req) · ACTION_LABELS
Every triage action — acknowledged, resolved, false_positive, reopened, auto_apply — appends one row with the actor and the IP it came from. IP extraction matches the attack detector exactly (first hop of x-forwarded-for, else x-real-ip), so a resolution IP and an attack IP are directly comparable. Reopening adds a row rather than erasing history. Writes here are best-effort — an audit failure never fails your action.

9 · Part H — Live Attacks (a completely separate pipeline)

The scanner is proactive — it goes looking for open doors once, when you run it. Live Attacks is reactive — it watches real traffic all the time. Different code, different table, different tab. No LangChain or LangGraph anywhere in this half.
Every single HTTP request
src/middleware.ts:105
Runs on the Edge runtime, before the /api early-return, so API traffic is covered too. Entirely wrapped in try/catch — detection can never break routing. Off unless SECURITY_DETECTION_ENABLED=1.
↓ splits in two
Traffic shape (per IP, over time)
src/lib/security/rate-watch.ts trackRequest({ip, path, method})
Called on every request — benign traffic has to be counted for the rates to mean anything. In-memory Map, 60s window, capped at 20,000 IPs, one event per IP per signal per 5 minutes so the detector can't become the DoS.
rate_flood (300 req/min) · path_enumeration (60 distinct paths/min) · auth_bruteforce (15 auth hits/min)
Payload content (this one request)
src/lib/security/detect.ts detectThreat(input) · detectBodyThreat(text)
Pure regex, Edge-safe, tuned for very few false positives — the blocking rules only match payloads that essentially never appear in real CRM traffic. Body scanning is separately opt-in via SECURITY_INSPECT_BODY=1 and reads a request.clone() so the route still gets its body.

Why LangChain here

  • One model interface. ChatOpenAI gives the same .invoke() whether the input is a bare prompt string (planning/triage) or a full message array (chat). Swapping the model is one env var: SECURITY_OPENAI_MODEL.
  • Token accounting for free. res.usage_metadata.input_tokens/output_tokens is what fills prompt_tokens / completion_tokens on the scan run — you can see what a scan cost.
  • Message-type discipline. SystemMessage/HumanMessage/AIMessage let the chat route replay a stored transcript with correct roles without hand-rolling the payload.
  • It degrades to nothing. Both makeModel() functions return null when OPENAI_API_KEY is unset. The scanner still finds everything; the chat still returns templated remediation text.

Why LangGraph here

  • The pipeline is a state machine, so write it as one. plan → probe → triage → write has real ordering constraints; the graph encodes them.
  • The reducer solves the token-summing problem. Two nodes both spend tokens; the (a,b) ⇒ a+b reducer on promptTokens merges them automatically.
  • Isolation. A node returning {} on failure keeps the run alive with a well-defined state. That's how a missing API key turns into a degraded scan rather than a crash.
  • It's honest about who's in charge. The LLM lives in exactly two nodes; the node that determines severity has no model in it at all. That boundary is visible in the graph, which matters a lot for a security tool.
What the AI is NOT allowed to do here
  • It cannot set or change severity (graph.ts:172 — “Severity is intentionally NOT read from the model”).
  • It cannot invent a finding — every finding object comes from a probe.
  • It cannot choose an arbitrary URL — parsePathArray() keeps only /api/ paths.
  • It cannot choose which file gets patched — resolve/route.ts re-locates the file itself.
  • It cannot make a fuzzy edit — the replacement must match exactly once or it's refused.

12 · Honest notes — dead code and real limits

1. The LangChain tool() definitions are currently unused. buildSecurityTools() in src/lib/security/agent/tools.ts:40 defines two proper LangChain tools (inspectPage, listKnownSurfaces) with zod schemas — but nothing calls it, and the model is never bindTools()-ed. The planner instead calls the plain function navigateAndInspect() directly and puts the result into the prompt text. So this is a single-shot prompt, not a tool-calling agent loop. The scaffolding is there for when someone wants the model to explore on its own.
2. security_findings.llm_model, prompt_tokens, completion_tokens are never written per-finding. The columns exist (E-215), but token counts are only rolled up onto security_scan_runs. LLM_MODEL_NAME is exported from graph.ts and never imported.
3. surfaces_walked is an estimate — it's the constant CURATED_SURFACE_COUNT (the four seed arrays added together, engine.ts:24), not a live count of what was actually hit.
4. The in-app Run Scan button only works where Chromium can launch. On Vercel serverless it returns 501 and tells you to use the CLI. On the Hostinger VPS it needs npx playwright install chromium.
5. Live detection is off unless two env vars are set — SECURITY_DETECTION_ENABLED=1 and SECURITY_INTERNAL_SECRET. Without the secret, postSecurityEvent() silently no-ops and the ingest route 503s.

What this system genuinely cannot see

  • Anything that bypasses the app. Someone with leaked credentials hitting RDS on 5432, S3, or Supabase with the service-role key never touches middleware. That needs CloudTrail and RDS logs.
  • A stolen session cookie. It is a valid authenticated request and looks identical to real use.
  • Failed passwords. Sign-in goes browser→Supabase directly, so wrong-password attempts are invisible; auth_bruteforce only sees request volume on the auth routes.
  • Real DDoS mitigation. rate_flood makes a flood visible; absorbing one belongs upstream — Cloudflare in front of the domain, limit_req in nginx.
  • Business-logic abuse by an authenticated user with a legitimate role.

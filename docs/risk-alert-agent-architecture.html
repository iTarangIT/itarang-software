CRM Risk Alert Agent

One agent that watches the whole iTarang CRM, catches risk anywhere in it, and tells the right person — in-app, by email, on WhatsApp.

LangGraph LangChain LangSmith Postgres Next.js cron route Architecture v1 · 28 Jul 2026

1. The problem in one picture

The CRM has ~253 tables and ~194 API routes. Today only a small corner of it is watched.

✔ Watched today

  • NBFC loan portfolio (risk cards)
  • Battery / IoT telemetry alerts
  • Rows explicitly put into the slas table

✘ Not watched at all

  • KYC review backlog piling up
  • KYC retries exhausted → dead lead
  • Orders past their delivery date
  • Stock stuck in “dispatched” forever
  • Dealer onboarding drafts abandoned
  • WhatsApp conversations gone silent
  • E-sign links expiring unsigned
  • Payments, consent gaps, data drift
And even where we do detect A High-severity risk card today is visible on one page and emails nobody. There is no delivery step. That is the gap this agent closes.

2. The one rule that makes it trustworthy

Golden rule The AI never decides severity or counts. Plain code does the maths. The AI only explains, groups, and drafts the message.

Why this matters: if you ask a model “how many leads are at risk?”, it will produce a number that looks exactly like a measured one and isn’t. So the numbers come from SQL, and the model gets the numbers handed to it.

This is the same discipline the existing NBFC risk engine already uses, so we keep the same four-word vocabulary:

VerdictWhat it actually means
HIGHWe tested it. It’s bad. Act now.
WARNWe tested it. It’s drifting. Keep an eye on it.
OKWe tested it and found nothing.
INCONCLUSIVEWe could not test it — data missing. This is not the same as OK.
ERRORThe check itself crashed. A bug in us, not a clean bill of health.

Collapsing those last three into “OK” is exactly how a broken engine renders as a healthy business. We don’t do it.

3. Architecture — six layers

Data comes in the top, an alert goes out the bottom. Only one layer uses AI.

1
Collectors — read the data
Plain SQL, one file per domain (leads, KYC, e-sign, EMI, inventory, payments, onboarding, telemetry, security). They return rows. They never judge anything.
IN 2 databases, read-only • OUT raw rows
▼
2
Detectors — decide the verdict
Deterministic TypeScript. Each detector is one small function: slug → fn(rows, thresholds) → findings. This is where HIGH/WARN/OK is decided, and nowhere else.
IN rows + thresholds • OUT RiskFinding[] — severity, counts, evidence
▼
3
Dedupe — is this actually new?
Every finding gets a fingerprint. Already open? Just bump the counter. Gone away? Close it automatically. This layer is what stops the inbox from becoming noise.
IN findings + open alerts • OUT new · reopened · still-open · auto-resolved
▼ (new findings only)
4
Triage — the only AI step 🤖
Takes a pile of raw findings and turns it into something a human can act on: groups related ones, ranks them, writes the explanation, picks the owner. See the breakdown below.
IN new findings (numbers already fixed) • OUT title, summary, recommended action, owner
▼
5
Notify — reach the human
In-app bell + email digest + WhatsApp for the urgent ones. Respects quiet hours and a suppression window. Escalates if nobody acknowledges.
IN triaged alerts + owner role • OUT bell · email · WhatsApp
▼
6
Dashboard + tracing
An alert board at /admin/risk-alerts to acknowledge / snooze / resolve, plus LangSmith traces so you can see what the agent did and what it cost.
IN the alert tables • OUT a screen a human works from

Layer 4 in detail — what does “triage” actually mean?

Triage, in one line Exactly like a hospital emergency room: many people arrive at once, someone decides who is seen first, and why. Our detectors are the people arriving. Triage is the nurse at the door.

Without triage, a sweep hands you 47 separate findings in no particular order, each phrased as a raw database condition. That is a spreadsheet, not an alert. Triage turns it into a short, ranked, readable list.

The five jobs triage does

JobWhat it meansExample
1 · Group Merge findings that share one root cause into a single incident, so you get one alert instead of forty. 38 separate “auto-debit failed” findings ➜ one alert: “Payment gateway looks down”
2 · Rank Order the incidents by what actually deserves attention first — money and compliance above process delays. A missing consent on a sanctioned loan ranks above 12 stalled leads
3 · Explain Rewrite the raw condition as three plain sentences: what happened · why it matters · what to do next. “retry_count ≥ 3” ➜ “4 customers can’t finish KYC. They’ll drop off. Call them or reset the verification.”
4 · Assign Pick the role that can actually fix it, so the alert lands on the right desk rather than everyone’s. Wallet low ➜ Finance Controller. Stalled lead ➜ Sales Manager.
5 · Suppress Mark findings that are real but not worth a ping right now — they stay on the dashboard, they just don’t interrupt anyone. 2 leads stalled over a public holiday ➜ visible, not notified

What triage is not allowed to do

AllowedForbidden
✔ Lower a severity (HIGH ➜ WARN) with a stated reason ✘ Raise a severity — ever
✔ Group findings and name the incident ✘ Invent a count, an amount, or a customer
✔ Write the summary and recommended action ✘ Change any number the detector computed
✔ Choose the owning role and the channel ✘ Create an alert no detector produced
✔ Mark something as not-worth-notifying ✘ Delete or resolve an alert

Enforced in code, not by prompt wording: the triage output is parsed through a strict zod schema, and any severity higher than the detector's own verdict is clamped back down before the alert is written. If the model returns nonsense, the alert still ships with the detector's raw wording — degraded, never wrong.

The practical test Turn triage off and the system still works — you just get the ugly 47-row list instead of the 3-line one. That is deliberate. Triage improves readability; it is never load-bearing for correctness.

5. The LangGraph flow

A straight line, not a loop. Predictable, cheap, easy to debug.

START→ collect_signals→ run_detectors→ dedupe_and_diff→ triage 🤖→ route_and_notify→ persist_run→ END

Two things to notice:

  • Triage is skipped when there are no new findings. Most sweeps cost ₹0 in tokens.
  • The graph is useful with the AI node switched off. The first release ships exactly like that. If the LLM never works, you still get a working alerting system.

State & durability

Standard StateGraph + Annotation.Root, compiled per call, no checkpointer — same as the two graphs already in this repo. Durability comes from writing rows to Postgres inside the nodes, not from LangGraph memory.

6. How dedupe works (the important bit)

Without this, every sweep re-raises every alert and everyone mutes the channel by Thursday.

fingerprint = sha1( detector_slug + entity_type + entity_id )

  e.g.  "kyc-retry-exhausted" + "lead" + "LEAD-10422"  →  a1f9c3…

One database index does the whole job:

CREATE UNIQUE INDEX risk_alerts_open_fingerprint_idx
  ON risk_alerts (fingerprint)
  WHERE resolved_at IS NULL;      -- only ONE open alert per fingerprint, ever

So on every sweep, each finding lands in exactly one of four buckets:

SituationWhat happensNotify?
New fingerprintCreate alert, status openYes
Already openBump occurrence_count + last_seen_atNo
Was resolved, came backReopen, log a reopened eventOnly after the suppression window
Open, but not found this sweepAuto-resolve, reason condition_clearedNo

Alert lifecycle

open→ acknowledged→ resolved ↘ also: snoozed · escalated to CEO

Every transition is written to an append-only risk_alert_events table, so “who knew what, when” is always answerable.

8. Keeping it quiet enough to be useful

An alerting system dies from noise, not from missing things. Eight controls, borrowed from Prometheus Alertmanager and PagerDuty.

Fewer false alarms

  • Fire-delay — must be true on two consecutive sweeps before it raises
  • Dedupe — one open alert per fingerprint, enforced by the DB
  • Auto-resolve — alerts close themselves when the condition clears
  • Severity ceiling — a new, unvetted detector cannot declare HIGH until a human promotes it

Lower cost & fewer pings

  • AI sees new findings only, batched one call per domain
  • Per-detector cap — and if we truncate, we log how many we dropped
  • Suppression window — same alert won’t re-ping for X hours
  • Quiet hours for email/WhatsApp; the in-app bell is always written

10. How it runs in production

Two schedules, hit by a normal VPS crontab — not a queue worker. (There is no live BullMQ worker in production; the repo’s real pattern is cron route → plain async function.)

*/15 * * * *   curl -X POST -H "Authorization: Bearer $CRON_SECRET" \
               "http://127.0.0.1:3002/api/cron/risk-alerts?scope=fast"

0    * * * *   curl -X POST -H "Authorization: Bearer $CRON_SECRET" \
               "http://127.0.0.1:3002/api/cron/risk-alerts?scope=full"
  • scope=fast — money + security detectors. Cheap, urgent, every 15 minutes.
  • scope=full — all four families, hourly.

A database-level lock (a partial unique index on “one running row per scope”) guarantees two sweeps can never overlap. A run stuck for 15 minutes is presumed dead and reaped, so a crash can’t wedge the system forever.

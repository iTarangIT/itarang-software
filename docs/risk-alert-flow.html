How a Risk Alert card gets made

The complete path from the Re-run analysis button to the cards on screen — every step, every table written, and every place a number could come from.

The one rule

The language model never states a verdict. It proposes questions and writes the code that answers them. Every severity and every count on this page is computed — either by a hand-written TypeScript evaluator, or by Python executed against real data. If we cannot compute it, the card says Inconclusive. It never says OK.

The 60-second version

Six stages, one click

The button fires a LangGraph workflow. It runs the same six nodes every time, in this order. Two of them talk to the language model; the rest are ordinary code and SQL.

Node 1 run_hand_coded Runs the 5 human-written evaluators. Pure TypeScript arithmetic — no AI involved at all.
Node 2 load_catalogue Loads the AI-authored hypotheses we already have, with the Python they were tested by.
Node 3 · LLM plan_dimensions Picks 3–4 risk themes to explore. Skipped entirely once we hold 12 hypotheses.
Node 4 · LLM propose_hypotheses Writes new hypotheses and the Python that tests each one. No code, no hypothesis.
Node 5 run_test Executes that Python in a sandbox against real loans + telemetry. This is the only place severity is decided.
Node 6 write_cards Persists one row per hypothesis to risk_card_runs. The page reads these.
Computes the numbers Talks to the LLM (proposes only — never judges) Reads / writes the database

Before the walkthrough

There are two kinds of card, and they behave differently

This is the single most useful thing to understand. Every card on the Risk page is one of these two — and the badge on the card tells you which.

source = "human" · no badge

Hand-coded cards (5 of them)

Written by us, reviewed by us, in hand-coded-cards.ts. Each is a TypeScript function that reads the loan book and the IoT telemetry and does the arithmetic itself.

They can raise a High Alert on their own authority, because a human wrote the test and a human agreed to the thresholds.

source = "llm-v1" · badge: AI

Agent-authored cards (up to 12 live)

The model invented the question and wrote the Python that answers it. The Python is stored and re-run every night, so the same test is measured over time — it is not re-invented each run.

Until a human promotes it, a card like this is capped at Warning. A machine-written test does not get to declare a crisis on its own say-so.

Why the cap matters. Without it, the model could invent a test like “vehicles that have an ignition status”, match 7 of 7 loans, and put a scarlet High Alert · 7 of 7 affected into a credit officer's queue — a statement that is technically true, completely useless, and indistinguishable from a real emergency.

End to end

The full walkthrough

Every step, in order, with the file that does it.

  1. The operator clicks “Re-run analysis”

    The button POSTs to the run endpoint with no body — the tenant is resolved from the session, not from the request. It then sits and waits: this is a synchronous call that blocks for roughly 30–60 seconds.

    POST /api/nbfc/risk/run  ·  src/app/(dashboard)/nbfc/risk/_components/RerunButton.tsx

  2. The route authenticates and resolves the tenant

    An NBFC partner may only run against a tenant they belong to; admin and CEO may run against any. The route caps itself at 120 seconds.

    src/app/api/nbfc/risk/run/route.ts  ·  getCurrentTenant() → requireNbfcAccess() → runRiskWorkflow()

  3. It takes a per-tenant lock — or returns 409

    A row is inserted into risk_runs with status = 'running'. A partial unique index on (tenant_id) WHERE status='running' means two callers physically cannot both win — the loser gets a unique violation and is turned into a 409: “Analysis already running — wait for it to finish.”

    Runs still marked running after 15 minutes are presumed dead and reaped, so a crashed process can't wedge the tenant forever.

    src/lib/nbfc/risk-run.ts  ·  beginRiskRun() · migration E-187

    Why: before this, double-clicking the button fired two complete workflows at the same tenant. Both wrote a full set of cards, and whichever finished last silently shadowed the other.

  4. Node 1 — the 5 hand-coded evaluators run

    The workflow pulls this tenant's active loans, resolves the governed thresholds once (so every card in the run is judged by the same numbers), then executes each human-written evaluator and writes its verdict straight to risk_card_runs with verdict_source = 'hand_coded'.

    If an evaluator throws — almost always because the IoT telemetry database is unreachable — the card is written as Error, not as OK.

    src/lib/risk/hand-coded-cards.ts  ·  HAND_CODED_CARDS (5 evaluators)

  5. Node 2 — load the AI hypothesis catalogue

    Loads every source = 'llm-v1' hypothesis that has not been retired and still has its stored Python. A hypothesis with no code cannot be re-run, so it is skipped rather than guessed at.

    src/lib/ai/langgraph/risk-hypothesis-graph.ts  ·  loadCatalogue()

    This is why 56 hypotheses exist but only 12 are live. Older AI rows were created before the Python was persisted alongside them. They still render as cards (their history is real), but they can never be re-executed — so they sit at Inconclusive or as legacy verdicts forever. Only rows that carry their own test code participate in a run.

  6. Nodes 3 & 4 — the LLM proposes (only if there's room)

    If the catalogue already holds 12 live hypotheses, both of these nodes do nothing. The run becomes a pure re-execution of the tests we already have, and the model is never called.

    Below 12, the model picks 3–4 risk dimensions, then for each one proposes hypotheses as JSON — slug, title, description, and mandatory Python defining evaluate(loans, vehicle_states, daily_km). A proposal with no code is discarded on the spot. New slugs are de-duplicated against the entire catalogue.

    Model: gpt-4o-mini (env NBFC_OPENAI_MODEL), temperature 0.2  ·  cap MAX_ACTIVE_LLM_HYPOTHESES = 12

    Why the cap: without it every click minted 6–8 fresh hypotheses, tested them once, and abandoned them. The catalogue reached 45 entries with only ~8 current, so the page filled with stale one-shot verdicts that reshuffled on every click.

  7. Node 5 — run the tests. This is the only place severity is decided.

    First the sandbox is health-checked once. Then the tenant's real data is fetched once and reused for every hypothesis: loans (from the CRM database), vehicle_states and 14 days of daily km (from the IoT telemetry database). Each hypothesis's stored Python is executed against those DataFrames.

    There is deliberately no LLM fallback here. Four outcomes, and only one of them is a verdict:

    What happenedCard becomesverdict_source
    Python ran, returned high / warn / ok High Warn OK sandbox
    Sandbox is down, or the IoT database is unreachable Inconclusive none
    Python ran but returned a severity we don't recognise Inconclusive none
    The generated Python raised, or the sandbox call failed Error none

    runTest()  ·  sandbox: services/risk-sandbox (FastAPI, bearer token)

    The sandbox is a real jail, not a figure of speech. It is a separate Python service that parses the model's code and rejects it unless every name is on an allowlist — pandas and numpy only. No imports, no eval, no open, no network. Execution runs in a child process capped at 30 seconds, 1 GiB, and zero subprocesses. We are executing code a language model wrote; it does not get to touch anything.

  8. Node 6 — write the cards (and apply the cap)

    Brand-new hypotheses are inserted into risk_hypotheses with their Python stored in test_definition, so tomorrow's run re-executes this exact test rather than inventing a new one. They start unpromoted.

    Then the cap is applied: an unpromoted AI hypothesis reporting High is written as Warning, with the reason appended to its critique and severity_capped flagged in its evidence. Finally one row per hypothesis lands in risk_card_runs.

    writeCards() · capUnpromotedSeverity()  ·  migration E-188

  9. Persistently broken tests retire themselves

    If an AI hypothesis's Python has errored on its last 3 consecutive runs, it is retired: retired_at and a reason are set. It keeps its full card history but is never executed or rendered again.

    retireIfPersistentlyBroken() · RETIRE_AFTER_CONSECUTIVE_ERRORS = 3

    Why: a generated test that always crashes isn't a risk signal, it's a bug — and left alone it would burn a sandbox slot every single night, forever.

  10. The run is closed out, and the summary comes back to the button

    The risk_runs row is marked completed with its counts and token usage — or failed with the error, so a dead run always carries a reason. The button turns that into the little line beside it: “10 of 12 hypotheses tested · 2 inconclusive”, then calls router.refresh().

    completeRiskRun() / failRiskRun()

  11. The page re-renders from the database

    The Risk page is a server component. It loads every non-retired hypothesis, finds the latest risk_card_runs row for each, and renders it. It does not re-compute anything — with one exception below.

    The first-load fallback: if a hand-coded hypothesis has no stored run at all, the page runs its evaluator live, on the spot, so a brand-new tenant isn't staring at an empty screen. That's why the header can say “Never run — these cards are computed live on page load.” An AI hypothesis with no stored run has no evaluator to fall back on, so it honestly renders as “Never tested.”

    src/app/(dashboard)/nbfc/risk/page.tsx  ·  loadCards()

Where the colour comes from

How a number becomes a severity

Every card computes a fraction — affected ÷ assessable — and compares it to two cutoffs. The cutoffs differ per card, because 1% of vehicles leaving their operating area is not the same kind of event as 1% of vehicles driving a bit less.

Hand-coded card What it measures High at Warn at Threshold source
usage-drop-7d Week-over-week collapse in km driven ≥ 5% ≥ 1% Governed — usage_drop_pct (default 40%)
dpd-7-no-telemetry Past-due and gone silent on GPS ≥ 3% ≥ 1% Governed — emi_overdue_days (30), offline_alert_hours (24)
geo-shift Vehicle far from its own 30-day home cluster ≥ 0.5% ≥ 0.1% Governed — geo_shift_km
battery-soh-decay > 5pp state-of-health drop in 30 days ≥ 2% ≥ 0.5% Hard-coded — no battery rule exists in the catalogue
low-utilization-active-loan Active EMI, averaging < 20 km/day ≥ 10% ≥ 4% Hard-coded window (14d, min 7 reporting days)
AI-authored cards AI Whatever the model proposed ≥ 5% ≥ 1% Rule-of-thumb given to the model in its prompt — then capped to Warn unless promoted
The denominator is the point. Each card scores against the population it can actually measure, not the whole loan book. A vehicle with no GPS history has no home base, so it is excluded from geo-shift rather than counted as “not diverted”. Vehicles that reported on fewer than 7 of the last 14 days are excluded from the utilisation card rather than counted as idle. That's what “4 / 5 affected” on a card means: four of the five loans we could assess — not four of five in the portfolio.

The part that's easy to miss

Five rails that stop the engine lying to you

Every one of these exists because the alternative already happened. This is the section worth dwelling on — it's the difference between an alert system and a random number generator.

Rail 1

“Inconclusive” is not “OK”

OK means we ran the test and found nothing. Inconclusive means we could not run the test. Error means the test blew up. Collapsing those three into a green OK is exactly what made a broken engine render as a healthy portfolio.

Rail 2

The LLM never states a number

Ask a model for an affected_count and it will produce one that looks exactly like a measured number and isn't. So it only ever writes the code. When we can't execute that code, we say so instead of guessing.

Rail 3

Unreviewed AI cards can't cry wolf

High → Warning, until a human promotes the hypothesis. You do that by opening the card and clicking Promote in the detail drawer — where you can read the question it asks, the code that answers it, and the rows it matched before you vouch for it. Retire sits next to it, for tests that are simply wrong.

Rail 4

Every card records what judged it

The thresholds in force are snapshotted into each card's evidence at run time. Without that, a card read six months from now would be silently reinterpreted against whatever the rules say then.

Rail 5

Cards go stale, and say so

Anything older than 36 hours is flagged Stale in the header — the nightly cron should have replaced it. A card carries the time it was produced, so a March number and a five-minute-old number no longer look identical.

Rail 6

The same test, every night

The Python is stored with the hypothesis and re-executed. That's what makes a card comparable to itself over time — previously the code was thrown away and next run invented an entirely different test.

Worth raising in the meeting

Every card in the current High Alert tab is badged AI — and that shouldn't be possible

An unpromoted AI hypothesis is capped at Warning. So a High Alert badged AI can only be one of two things: a hypothesis a human has explicitly promoted, or a legacy row written before the cap existed — which is exactly what the violet 16-card banner above it is warning about.

That is the banner and the High Alert tab describing the same problem. Re-running the analysis is what resolves it: those 16 legacy cards get replaced with computed verdicts, and any AI card that still wants to be a High Alert has to be promoted by a human first.

The other trigger

Nobody is supposed to need that button

The button exists for an operator who wants an answer now. What actually keeps the cards fresh is a nightly cron on the VPS, at 01:30, which sweeps every active tenant through the identical workflow:

30 1 * * *POST /api/cron/nbfc/risk-analysis  (Bearer CRON_SECRET)

It takes the same per-tenant lock, so a cron sweep that collides with someone's manual click is skipped, not queued. And one tenant's failure doesn't abort the sweep for the rest — its run row is marked failed with the reason, and the loop moves on.

Where it all lands

The three tables

TableHoldsKey columns

Scope, stated plainly. The engine's only input from the CRM database is nbfc_loans — it does not read borrower_risk_scores or emi_schedules. Everything else it knows comes from the IoT telemetry database. And this flow writes no alert rows and no audit-log entries: the Action Framework table at the bottom of the Risk page describes the approval and audit chain — it doesn't execute one. If your team leader asks “where does the alert go”, the honest answer today is: it goes on this page, and nowhere else.

Anticipated

The questions you'll get asked

“So is this thing AI, or is it rules?”

Both, and the split is the whole design. The AI's job is generating the questions — it proposes hypotheses a human might not have thought to write, and it writes the code to test them. The answers are always computed: hand-written TypeScript for the 5 core cards, sandboxed Python for the AI ones. The model is a research assistant, not a judge.

“Why does it say 35 of 56 — what happened to the other 21?”

They have no computed verdict. Either they're legacy rows from before we tracked provenance (the 16 in the violet banner), or their test couldn't run this time — sandbox down, telemetry unreachable, or the generated Python crashed. The page refuses to present those as measurements. Re-running is what shrinks that gap.

“Can the AI put a false emergency in front of a credit officer?”

Not on its own. An AI hypothesis nobody has reviewed is capped at Warning, no matter what its Python computes. To become a High Alert it has to be promoted by a human, which is a deliberate action on a specific endpoint. The High Alerts visible today are legacy rows that pre-date that cap — see the callout above.

“What happens if the IoT telemetry database is down?”

The run still completes, and every card that needed telemetry says it wasn't tested — a coverage gap, not an engine failure. The page shows an amber banner naming the problem. Critically, none of those cards turn green: an unreachable database can never be mistaken for a healthy portfolio.

In local development this is the single most common cause of a page full of Inconclusive cards — the IoT database is only reachable through the ssh -N iot-bastion tunnel.

“Does clicking the button twice run it twice?”

No. The second click gets a 409 and the message “Analysis already running — wait for it to finish.” The lock is a database constraint, not a check in application code, so it holds even across separate processes — the nightly cron and a manual click can't collide either.

“Why doesn't the catalogue just keep growing?”

It's capped at 12 live AI hypotheses. At the cap, a run proposes nothing and simply re-executes the tests it already has — which also means it skips both LLM calls entirely and costs nothing in tokens. Tests that crash on 3 consecutive runs retire themselves out of the pool.

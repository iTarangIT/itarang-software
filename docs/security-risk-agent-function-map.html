01The three pipelines

The subsystem is three independent pipelines that share a database and a dashboard, but no runtime code path. Understanding which one you're in is the whole game.

PIPELINE A — PROACTIVE

Security Scanner

Drives a real Playwright browser through the CRM as several logged-in roles, actively probes for vulnerabilities, and records findings. Runs on demand (CLI / button), not continuously.

security_scan_runs · security_checks · security_findings
PIPELINE B — REACTIVE

Live-Attack Detector

A WAF-style layer inside middleware.ts that inspects every real request, blocks high-confidence attacks and logs them. Always on (once opted in).

security_events
PIPELINE C — REMEDIATION

AI Resolution + Auto-Apply

Per-finding chat with an agent that has read the real source file, then a deterministic single-occurrence patch written to disk with backup + rollback.

security_finding_messages · security_finding_actions · security_findings
Not the NBFC risk engine. This document covers the IT Security agent only. A second, unrelated agent exists — the NBFC Risk agent (src/lib/risk/, src/lib/ai/langgraph/risk-hypothesis-graph.ts, tables risk_hypotheses / risk_card_runs / risk_runs, UI /nbfc/risk, Python sandbox on 127.0.0.1:8091). They share no tables and no code — only house style. Both the E-215 migration header and schema.ts:9271 say it outright: "Do not join these tables to the risk_* family." Different severity ladders too — security uses critical…info, NBFC risk uses high|warn|ok|inconclusive|error.

05Pipeline A · run lifecycle & the single-flight lock

src/lib/security/scan-run.ts

FunctionInputOutputReadsWritesCalled by
beginScan(input)Opens a new scan record and claims the lock, so two scans can't run against the same environment at once. failScan(runId, error)Marks the scan as failed and stores the error message that killed it. runId: string, error: unknown Promise<void> — security_scan_runs UPDATE status='failed', error, finished_at runSecurityScan() catch block
getScanFreshness(env?)Tells the dashboard when the last scan ran and whether one is running right now. env?: TargetEnv ScanFreshness { last_run_at, status, is_stale, in_flight } — is_stale after STALE_AFTER_HOURS = 168 (7 days) security_scan_runs — GET /api/it/security/scan/status, /it/security page
The lock is a database constraint, not application code. security_scan_runs_env_running_uidx is a partial unique index on (target_env) WHERE status = 'running' — declared in drizzle/E-215_security_scanner.sql only, not in schema.ts. A second concurrent scan against the same environment fails the INSERT in beginScan(), which converts the pg 23505 into a ScanInFlightError → the run route answers 409 "A scan is already running." A crashed scan would hold the lock forever, so beginScan() calls reapStaleRuns() first — anything running for more than RUN_TIMEOUT_MINUTES = 30 is marked failed.

07Pipeline A · the engine

src/lib/security/engine.ts

FunctionInputOutputReadsWritesCalled by
runSecurityScan(opts)The conductor — sets everything up, runs the steps in order, and always closes the browser afterwards. RunScanOptions { targetUrl?, mode?, trigger, actorUserId?, roles?, log? } RunScanResult { runId, summary, skippedRoles } — (delegates) — (delegates) CLI · POST /scan/run
fingerprint(f, path) privateBuilds a stable ID for a finding so the same bug isn't recorded twice across scans. RawFinding, path: string string — sha256(check_slug|http_method|path|title), first 64 chars —— persistFindings()
persistFindings(runId, baseUrl, raw) privateSaves the findings to the database, refreshing existing rows instead of piling up duplicates. runId, baseUrl, raw: RawFinding[] Promise<ScanSummary> — per-severity counts + surfaces_walked — security_findings INSERT … ON CONFLICT (fingerprint) WHERE status <> 'resolved' DO UPDATE passed to the graph as deps.persist

The orchestration order inside runSecurityScan():

resolveTarget(opts.targetUrl)  →  { baseUrl, env }
resolveMode(opts.mode)         →  mode
beginScan({...})               →  runId          ── acquires the env lock
launchBrowser()                →  browser
loginRoles(browser, baseUrl)   →  sessions, skipped
playwrightRequest.newContext() →  anon  (no cookies)  +  one ctx per role
build ProbeContext             →  { baseUrl, targetEnv, mode, browser, anon, api, storage, log }
runSecurityGraph({ ctx, persist })
completeScan(runId, summary)                       ── or failScan(runId, e) on throw
finally: dispose every APIRequestContext, close the browser
Deduplication is two-layered. Within one run, a Set of fingerprints drops repeats before the INSERT. Across runs, the partial unique index upserts the existing row — refreshing severity, summary, evidence_json and run_id, but deliberately never touching the human triage status. A resolved finding that reappears creates a brand-new row, because the index excludes status='resolved'.

What this system does NOT catch. Anything that bypasses the app entirely — direct RDS on 5432, S3, Razorpay's API, Supabase with the service-role key — never touches middleware and produces zero events. A stolen session cookie is a valid authenticated request and is indistinguishable from real use. Failed passwords are invisible (sign-in goes browser → Supabase directly, so auth_bruteforce only sees request volume). And rate_flood makes a flood visible but does not mitigate it — volumetric defence belongs upstream in Cloudflare and nginx limit_req.
